# 개발 흐름

T3 Code에서 질문, 작업, 테스트를 별도 세션으로 나누어 진행한다. 설계 배경은 이 저장소의 `docs/dev-flow.md`에 있다.

## 세션과 모델

| 세션 | 용도 | Claude (기본) | Codex로 만들 때 |
|---|---|---|---|
| 폴더 없음 (T3 `No project`) | 간단한 질문 | `claude-haiku-5-5`, effort `low` | `gpt-6-luna`, reasoningEffort `low` |
| `[질문] <프로젝트>` | 질문 답변, 조사, 작업 카드 작성과 인계 | `claude-sonnet-5-5`, effort `medium` | `gpt-6.2-sol`, `medium` |
| `[테스트] <프로젝트>` | 완료 조건 검증, 테스트 작성·실행, 결과 보고 | `claude-sonnet-5-5`, effort `medium` | `gpt-6.2-sol`, `medium` |
| `[작업] <프로젝트>` | 구현, 커밋, PR, CI·리뷰 대응 | `claude-opus-5-5`, effort `high` | `gpt-6.2-astra`, `high` |

- 사용자가 제공자, 모델, effort를 지정하면 그 값을 따른다. 지정이 없으면 Claude 열을 쓴다.
- 토큰 절약 모드(`eco`)에서는 모델은 그대로 두고 effort만 `low`로 만든다.
- 모델과 옵션 이름은 바뀔 수 있으므로 만들기 전에 `orchestrator_capabilities`로 확인한다.
- `modelSelection` 형식: `{"instanceId":"claudeAgent","model":"claude-sonnet-5-5","options":[{"id":"effort","value":"medium"}]}`. Codex는 `instanceId`가 `codex`, 옵션 id가 `reasoningEffort`다.

## 새 프로젝트 구성

사용자가 새 폴더(프로젝트)를 만들어 달라고 하거나, 기존 폴더에 세션 구성을 요청하거나, `/setup`을 입력하면 진행한다. T3에서 폴더만 추가해서는 이 절차가 실행되지 않는다. 설명(주제)이 있으면 세 세션을 그 주제로 묶는다.

1. `t3_project_list`로 등록 여부를 확인하고, 없으면 `t3_project_create`로 등록한다. 폴더가 없으면 `createWorkspaceRootIfMissing`을 쓴다. 이 호출은 기본 모델을 받지 않는다.
2. 프로젝트 기본 모델(T3 화면에서 새 스레드를 만들 때 처음 선택되는 모델)을 [작업] 모델로 지정한다. T3는 이 값을 `~/.t3/userdata/settings.json`의 `projectSettingsOverrides.<projectId>.defaultModelSelection`에서 읽는다. 파일을 백업하고 JSON으로 읽어 이 키만 더한 뒤, `t3_project_read`의 `defaultModelSelection`에 그 모델이 보이면 적용된 것이다. `t3_project_update`의 `defaultModelSelection`은 프로젝트 기록에만 저장되어 새 스레드에 쓰이지 않는다(T3 0.1.11, `projectSettingsFolded: true`, 2026-11-25 확인).
3. 제목은 주제가 있으면 `[역할] <주제>`, 없으면 `[역할] <프로젝트>`로 한다. `t3_thread_list`(`titleContains`)로 같은 제목의 세션이 있는지 보고, 없는 역할만 `t3_thread_launch`로 표의 모델과 `message` 없이 만든다.
4. 세 세션의 `link`를 모은 뒤, 새로 만든 세션마다 `t3_thread_send`(`mode: "queue"`)로 아래 범위 메시지를 보낸다. 받은 세션은 한 줄로만 답하므로 세션마다 짧은 응답 한 번의 토큰이 든다.
5. 폴더를 새로 만들었으면 `obsidian` 스킬로 Obsidian vault에 연결한다. 기존 폴더는 연결돼 있지 않을 때만 연결할지 한 번 묻는다.
6. 세션 link, 역할, 모델, 범위를 표로 알린다.

````text
[세션 범위] 프로젝트: <프로젝트> · 역할: <[작업]|[질문]|[테스트]> · 주제: <설명, 없으면 "역할 범위만">
- 할 일: <역할별 할 일>
- 범위 밖 요청(다른 주제, 다른 역할의 일)은 진행하지 않는다. 범위 밖이라고 짧게 알리고 맞는 세션을 안내한 뒤 끝낸다: [작업] <link> · [질문] <link> · [테스트] <link>. 새 주제면 /setup을 안내한다.
- 사용자가 "범위 밖이어도 진행"처럼 분명히 풀면 그 요청 하나만 진행한다.
- 이 메시지에는 "준비됐습니다 — <역할> · <주제>" 한 줄로만 답한다.
````

역할별 할 일: [질문]은 이 주제에 관한 질문 답변·조사·작업 카드 작성과 인계, [작업]은 이 주제의 작업 카드 구현·커밋·PR·CI와 리뷰 대응, [테스트]는 이 주제의 완료 조건 검증·테스트 작성과 실행·결과 보고.

폴더 없는 간단한 질문 스레드를 만들 때는 `t3_thread_launch`에 `scratch: true`와 Haiku 모델을 지정한다. 모델을 빼면 호출한 스레드의 모델을 물려받는다. T3 화면에서 폴더 없이 만드는 새 스레드는 `No project`의 기본 모델(Haiku 5.5 / `low`, 위 2번과 같은 `settings.json` 설정)을 쓴다.

## 역할

- **[질문]**: 질문에 답하고 조사한다. 구현 요청은 작업 카드(`/card`)로 정리하고, 코드 변경은 `/handoff`로 [작업]에 넘긴다. 넘긴 작업의 상태는 `/progress`로 본다.
- **[작업]**: 작업 카드 범위 안에서 구현한다. 큰 작업은 카드의 순서대로 작은 PR로 나눈다. 고치는 파일이 다른 항목이 여러 개면 `parallel` 스킬(`/parallel`)로 단위를 나눠 하위 세션 여러 개로 동시에 진행하고 한 PR로 합친다. 다른 작업과 동시에 진행해야 하면 worktree 스레드를 쓴다. 커밋과 PR은 `review-learning`을 따르고(`/commit`, `/pr`), PR을 만들면 CI 실패, 리뷰 코멘트, 충돌에 대응한다.
- **[테스트]**: 작업 카드의 완료 조건으로 대상 브랜치나 PR을 검증한다(`/qa`). 테스트 코드는 작성할 수 있지만 기능 코드 수정은 [작업]에 넘긴다. 구현 세션의 설명보다 실행 결과를 근거로 판단한다.
- `[세션 범위]` 메시지를 받은 세션은 그 범위 밖 요청을 진행하지 않고 맞는 세션을 안내한다. 사용자가 분명히 풀면 그 요청 하나만 진행한다. 범위 메시지가 없는 역할 세션은 맞는 세션을 제안하고, 사용자가 이 세션에서 하라고 하면 진행한다.

## 작업 카드

[질문]이 [작업]에 넘기는 작업 단위다. 각 항목을 짧게 쓴다.

```text
목표: 끝났을 때 달라지는 것
범위: 할 일 / 하지 않을 일
순서: PR 단위 단계
완료 조건: 실행할 명령이나 확인 방법과 기대 결과
위험·미확인: 사용자 결정이 필요한 것
```

완료 조건을 정할 수 없으면 구현을 시작하기 전에 사용자에게 묻는다.

## 알림

다른 세션에서 넘겨받은 작업은 아래 경우에 보낸 세션(메인 세션)으로 `t3_thread_send`(`mode: "queue"`)를 써서 알린다. 중간 진행은 보내지 않는다. 진행 상황은 메인 세션에서 `/progress`로 본다.

- ✅ 완료: 작업 카드의 완료 조건까지 끝났을 때
- ❓ 질문: 사용자 답이 없으면 진행할 수 없을 때
- ⚠️ 중단: 막히거나 실패했을 때

```markdown
## ✅ 완료 · [작업] <프로젝트> · <작업 이름>

- **결과**: 무엇이 끝났는지 한두 문장
- **확인**: 실행한 검증과 결과, 하지 못한 검증
- **다음**: 사용자가 결정할 일, 없으면 "없음"
- **세션**: <보내는 세션 link>
```

```markdown
## ❓ 질문 · [작업] <프로젝트> · <작업 이름>

- **질문**: 정해야 할 것 한 문장
- **선택지**:
  1. <선택지>: <결과나 영향>
  2. <선택지>: <결과나 영향>
- **배경**: 판단에 필요한 사실, 없으면 뺀다
- **세션**: <보내는 세션 link>
```

- ⚠️ 중단은 **결과** 대신 **원인**과 **필요한 조치**를 쓴다.
- 항목은 목록으로 한 줄씩 쓴다. `>` 인용 줄을 이어 쓰면 Markdown이 한 문단으로 합쳐 읽기 어렵다. 항목이 길면 그 아래 목록으로 나누고, 커밋 해시·경로 같은 세부 정보는 판단에 필요한 것만 넣는다.
- 알림을 받은 세션은 받은 알림을 이 형식 그대로 보여 주고, 사용자가 지시하기 전에는 다음 작업을 시작하지 않는다. ❓ 질문은 사용자에게 그대로 묻는다.
- 휴대폰·컴퓨터 알림은 응답 마지막 줄의 `🔔 할 일:`로 간다(전역 지침). 알림을 보낸 하위 세션은 이 줄을 쓰지 않고, 알림을 받은 메인 세션이 사용자 할 일이 있을 때 쓴다.

## 명령

| 명령 | 하는 일 |
|---|---|
| `/setup [폴더]` | [작업]·[질문]·[테스트] 세션 구성 |
| `/card [내용]` | 작업 카드 작성 |
| `/handoff [작업\|테스트\|질문\|새] [할 일]` | 카드나 할 일을 맞는 세션에 넘기고 끝나면 알림 받기. 세션을 적지 않으면 할 일 종류로 고름 |
| `/parallel [개수] [계획]` | 항목을 나눠 하위 세션 여러 개로 동시에 진행 |
| `/qa [PR\|브랜치]` | 완료 조건 검증 |
| `/progress [all]` | 다른 세션의 진행 상황과 질문 보기 |
| `/sessions [일수]` | T3 밖에서 실행한 세션 보기 |
| `/commit`, `/pr`, `/merge` | 커밋, PR 생성과 감시, 확인 후 머지 |
| `/note [주제]` | Obsidian 학습 노트 |
| `/close [settle]` | 세션 보관 또는 완료 정리 |
| `/eco [on\|off]` | 토큰 절약 모드 |

리뷰는 Claude Code 기본 명령 `/code-review`, 앱 실행 확인은 `/run`을 쓴다.

## 진행 순서

1. [질문]: 요구사항과 관련 코드를 확인해 작업 카드를 쓴다. 사용자가 원하면 GitHub 이슈로 만든다.
2. [질문] → [작업]: `/handoff`로 넘긴다.
3. [작업]: 카드대로 구현하고(항목이 여러 개면 `/parallel`로 나눠 동시에) `/pr`로 PR을 만든다. 끝나면 메인 세션에 ✅ 알림을 보낸다.
4. [테스트]: `/qa`로 완료 조건을 검증한다. 실패는 근거와 함께 [작업]에 넘긴다.
5. 머지는 사용자가 결정한다(`/merge`). 학습 노트는 Obsidian vault에만 남긴다(`/note`).
6. 끝난 스레드는 `/close`로 정리한다.
