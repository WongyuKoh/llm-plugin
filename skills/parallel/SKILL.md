# 병렬 진행

맡은 항목을 단위로 나눠 하위 세션 여러 개가 동시에 구현하고, 이 세션이 결과를 합쳐 PR 하나로 만든다. 인자: `$ARGUMENTS`. 숫자는 동시에 띄울 하위 세션의 최대 개수(기본 4)다. `계획`이 있으면 나눈 표만 보이고 멈춘다.

## 주제로 묶기

요청이 서로 다른 화면이나 기능에 걸치면 비슷한 항목끼리 주제로 묶고, 주제마다 하위 세션 하나와 PR 하나를 둔다. 주제 하위 세션에 보내는 지시에 "맡은 항목은 parallel 스킬(`~/.claude/skills/parallel/SKILL.md`)의 '단위로 나누기'부터 따라 동시에 진행한다. 하위 세션 최대 N개"를 넣는다. 하위 세션은 지시에 있어야 다시 하위 세션을 만든다. 주제가 하나면 바로 단위로 나눈다.

## 단위로 나누기

1. 항목마다 고칠 파일을 코드에서 확인한다(검색, import 관계, 받은 지시의 '확인한 사실'과 '경계'). 짐작으로 나누지 않는다.
2. 고칠 파일이 겹치는 항목은 한 단위로 묶어, 단위끼리 고치는 파일이 겹치지 않게 한다. 번역 JSON처럼 합칠 때 기계적으로 풀리는 파일만 예외다.
3. 여러 항목이 함께 고치는 공통 파일(툴바, 페이지 컴포넌트 등)이 든 단위는 이 세션이 직접 맡고, 나머지 단위를 하위 세션에 보낸다.
4. 공통 파일 때문에 나누기 어려우면 먼저 공통 부분을 떼어 내는 작은 준비 커밋(컴포넌트 파일 분리 등)을 하고 나눈다.
5. 항목이 작아 금방 끝나거나, 대부분 같은 파일을 고치거나, 앞 항목의 결과가 있어야 다음 항목을 할 수 있으면 나누지 않거나 개수를 줄인다. 나누지 않으면 이유를 한 줄로 알리고 직접 진행한다.
6. 단위마다 크기를 보고 담당을 정한다. 다시 나눌 만큼 큰 단위는 연계 세션(아래 '큰 단위는 연계 세션으로'), 나머지는 하위 세션이나 이 세션이다.
7. 단위 · 맡은 항목 · 고칠 파일 · 브랜치 · 담당(이 세션, 하위 세션, 연계 세션)을 표로 알린다. `계획`이면 여기서 멈춘다.

## 큰 단위는 연계 세션으로

단위 하나가 그 안에서 다시 나눌 만큼 크면 하위 세션(`delegate_task`)으로 보내지 않는다. 대신 사이드바에 따로 보이는 별도 세션(연계 세션)을 만들고, 그 세션이 다시 이 스킬로 나눠 진행하게 한다. 하위 세션은 끝나면 T3가 정리하고 결과 보고가 이 세션에 쌓이지만, 연계 세션은 사용자가 따로 열어 보고 대화하고 이어갈 수 있다.

큰 단위로 보는 경우:
- 단위 안에 서로 다른 파일을 고치는 항목이 셋 이상이라 그 안에서도 나눠야 할 때
- 서로 다른 영역(예: 화면과 서버, 스키마와 마이그레이션)에 걸쳐 따로 검토·검증이 필요한 크기일 때
- 오래 걸려 진행 보고와 질문이 이 세션의 컨텍스트를 많이 차지할 것 같을 때
- 사용자가 연계 세션으로 하라고 할 때

애매하면 하위 세션으로 보낸다.

만드는 법:
1. 이 세션의 변경을 먼저 커밋한다. 연계 세션은 이 세션 브랜치의 마지막 커밋에서 시작한다.
2. `t3_thread_configure`(인자 없음)로 이 세션의 threadId를, `t3_thread_read`(`limit: 1`)로 제목과 브랜치를 확인한다.
3. 단위마다 `t3_thread_launch`를 부른다.
   - `title`: `↳ <이 세션 제목> · <단위 이름>`. 이 세션이 이미 연계 세션(`↳`로 시작)이면 앞의 `↳ `를 떼고 같은 형식으로 붙여 `↳ <원래 제목> · <상위 단위> · <단위 이름>`처럼 이어지게 한다.
   - `workspaceStrategy`: `{ type: "worktree", baseRef: <이 세션 브랜치>, branch: "<이 세션 브랜치>-<번호>-<이름>", startFromOrigin: false }`. worktree를 셸에서 직접 만들지 않는다.
   - 모델과 모드는 넣지 않는다(이 세션 것을 물려받는다). `delegatedFrom`은 쓰지 않는다.
   - `message`: 아래 연계 세션 지시. 하위 세션 지시와 같은 내용에 '다시 나누기'와 '보고'가 더해진다.
4. 연계 세션의 결과는 ✅·❓·⚠️ 알림으로 이 세션에 들어온다. 결과를 기다리려고 연계 세션을 반복해서 읽지 않는다. ❓ 질문에 이 세션이 답할 수 있으면 `t3_thread_send`로 답하고, 사용자 결정이 필요하면 사용자에게 그대로 묻는다.
5. ✅가 오면 하위 세션 단위와 같이 '합치기'로 합친다. 연계 세션의 worktree도 같은 저장소의 git worktree라서 브랜치 이름으로 바로 합칠 수 있다.

````text
[연계 작업] 원래 세션: <이 세션 threadId> · <이 세션 제목>
너는 원래 세션의 단위 <번호> · <단위 이름>을 맡은 연계 세션이다. 아래 항목을 구현하고 커밋까지 한다. 보고는 한국어로 쓴다.

## 공통 지침
- 저장소: <경로>. 이 worktree는 <이 세션 브랜치>의 <SHA>에서 시작했고 브랜치는 `<연계 브랜치>`다. 이 브랜치에 커밋한다. 푸시와 PR은 하지 않는다(원래 세션이 합친다).
- 따를 규칙: <CLAUDE.md 등 저장소 규칙, 커밋 메시지 형식>
- 검증: <이 단위에서 실행할 명령>
- 포트: <개발 서버를 띄울 때 쓸 포트, 필요할 때만>
- 해석이 갈리면 합리적인 기본값으로 진행하고 보고에 적는다.

## 맡은 항목 (사용자 요청 원문)
- <항목>

## 확인한 사실
- <관련 파일, 함수, 현재 동작>

## 경계
- 고칠 파일: <목록>
- 고치지 말 것: <다른 단위나 원래 세션이 맡은 파일>. 꼭 바꿔야 하면 고치지 말고 보고의 '필요한 변경'에 적는다.

## 다시 나누기
- 맡은 항목은 parallel 스킬(`~/.claude/skills/parallel/SKILL.md`)의 '단위로 나누기'부터 따라 동시에 진행한다. 하위 세션 최대 <N>개.
- 하위 세션 브랜치는 `<연계 브랜치>-<번호>-<이름>`으로 만들고, 이 세션 브랜치에 합친다.

## 보고
- 끝나면 ✅ 완료, 사용자 답이 필요하면 ❓ 질문, 막히면 ⚠️ 중단 알림을 t3_thread_send(threadId: <이 세션 threadId>, mode: "queue")로 보낸다. 중간 진행은 보내지 않는다. 형식은 dev-flow 스킬의 알림 형식을 따르고, 제목의 세션 표시는 `<연계 세션 제목>`으로 쓴다.
- ✅ 완료의 **결과**에 단위별 변경을, 마지막 줄에 `브랜치 <연계 브랜치>, head <SHA>`를 쓴다.
- 보고 받을 세션이 바뀌었다는 메시지를 받으면 그 뒤로는 새 세션에 보낸다.
- 이 세션의 응답에는 `🔔 할 일`을 쓰지 않는다. 사용자 알림은 원래 세션이 보낸다.
````

## 하위 세션 띄우기

- 이 세션의 변경을 먼저 커밋한다. 하위 세션은 이 세션의 마지막 커밋에서 시작하고, 커밋하지 않은 변경은 받지 못한다.
- 단위마다 `delegate_task`를 `isolation: "worktree"`, `role: "implementation"`, `title: "[작업] <주제> · <단위>"`로 부른다. 모델을 정하지 않으면 이 세션과 같다. worktree를 셸에서 직접 만들지 않는다.
- 하위 세션은 이 대화를 볼 수 없으므로 아래 형식에 필요한 사실을 모두 넣는다. 이 세션이 받은 지시가 있으면 그 공통 지침(저장소 규칙, 검증 명령, 샌드박스·포트 안내)을 그대로 옮긴다.
- 모두 띄운 뒤 이 세션의 단위를 진행한다. 하위 세션의 결과는 끝나면 들어오므로 `task_status`를 반복 호출하거나 sleep으로 기다리지 않는다.

## 합치기

1. 모든 단위가 끝나면 이 세션의 브랜치에서 단위 브랜치를 하나씩 `git merge --no-ff <단위 브랜치>`로 합친다. T3 하위 세션의 worktree는 같은 저장소의 git worktree라서 브랜치 이름으로 바로 합칠 수 있다. 충돌은 양쪽 의도를 살려 푼다.
2. 단위가 보고한 '필요한 변경'을 반영하고, 완료 조건의 전체 검증(타입 검사, 린트, 테스트 등)을 실행해 고친다.
3. `/pr` 절차로 PR을 만들거나 기존 PR을 갱신한다. 본문에 단위별 변경을 적는다.
4. 단위 · 결과 · 브랜치 · 검증을 표로 보고한다. 넘겨받은 작업이면 `dev-flow` 알림 규칙대로 메인 세션에 알린다.

하위 세션이 질문으로 멈추면 이 세션이 답할 수 있는 것은 `t3_thread_send`로 답하고, 사용자 결정이 필요하면 `dev-flow` 알림 규칙대로 ❓ 질문을 보낸다. 실패한 단위는 이 세션이 이어서 하거나 다시 띄운다.

## 주의

- 하위 세션마다 토큰과 이 Mac의 자원(의존성 설치, 개발 서버)이 든다. 기본 최대 4개는 이 때문이고, 사용자가 개수를 정하면 따른다. 연계 세션도 이 세션의 개수에 센다. 연계 세션 안의 하위 세션 수는 지시에 적은 `<N>`을 따른다.
- 연계 세션은 끝나도 T3가 정리하지 않는다. 합친 뒤 필요 없으면 `/close`로 정리한다.
- 토큰 절약 모드(`eco`)에서는 나누지 않는다.
